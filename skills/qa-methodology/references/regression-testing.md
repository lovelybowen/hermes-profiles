# 回归测试

## 应纳入回归套件的内容

| 纳入 | 排除 |
|---------|---------|
| 每个已修复缺陷（作为测试） | 六个月以上未失败的测试（归档） |
| 关键用户路径 | 已弃用功能的测试 |
| 已知失败模式 | 与低层覆盖重叠的测试 |
| API 契约检查 | 开发中 UI 的视觉回归测试 |
| 数据完整性断言 | 性能测试（单独套件） |

## 套件卫生

| 情况 | 行动 |
|-----------|--------|
| 测试六个月未失败 | 考虑归档，它可能不再测试有意义内容 |
| 10 次运行中不稳定率超过 1% | 立即调查、修复或删除 |
| 测试耗时超过 5 秒（单元）/ 30 秒（集成） | 优化或提升到更慢层级 |
| 测试依赖其他测试的状态 | 修复隔离性，测试必须独立 |
| 测试使用生产数据 | 切换到合成夹具 |

## 基于变更的测试选择

并非每项变更都需要完整回归套件。针对定向变更：

| 变更类型 | 必需测试 |
|-------------|---------------|
| 缺陷修复 | 可复现缺陷的测试，加上相关单元测试 |
| 新增功能 | 新功能测试，加上相邻领域的冒烟测试 |
| 重构 | 完整单元套件，加上集成冒烟测试 |
| 配置变更 | 受影响组件的冒烟测试 |
| 依赖更新 | 完整回归套件 |
| 基础设施变更 | 集成加 E2E 套件 |
