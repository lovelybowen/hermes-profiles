# 技术验证路径

适用于可以通过执行操作检验的主张，例如运行代码、查询 API、检查基准测试和自行测量。最可信的证据是可以自行复现的证据。

## 核心原则

如果主张建立在数值、基准测试或可观察行为之上，且你具备测试工具，就不要只依赖来源的主张。亲自测试；正确开展的自行测量属于一级来源。

## 应通过测试验证的内容

| 主张类型 | 测试方法 | 工具 |
|------------|-------------|------|
| **性能数值**（延迟、吞吐量、显存使用） | 使用相同参数复现基准测试 | 终端、Python 脚本 |
| **API 行为**（“API 在 Y 条件下返回 X”） | 使用文档参数调用 API | curl、Python httpx |
| **模型输出**（“模型 A 在 X 上优于模型 B”） | 使用相同提示词运行两个模型 | llama.cpp、OpenRouter API |
| **配置主张**（“设置标志 X 可获得最佳结果”） | 分别开启和关闭标志后比较 | 终端、A/B 测试 |
| **内存或磁盘使用**（“使用量小于 X”） | 构建系统并测量实际使用量 | `du`、`ps`、`nvidia-smi`、`htop` |
| **可用性主张**（“协议支持 Y”） | 阅读规范，再尝试执行 | 源代码、协议文档、实际实现 |
| **兼容性主张**（“适用于 macOS 和 Linux”） | 在两个平台测试，或验证各平台 CI 结果 | CI 日志、Docker |

## 复现标准

### 步骤 1：仔细阅读主张
来源究竟主张什么？写下具体数值、标志、参数和条件。

### 步骤 2：复现条件
使用相同的：
- 模型版本或软件版本。
- 硬件，或可比较的硬件。
- 配置标志。
- 输入数据，或等效数据。
- 测量方法。

如果来源没有完整说明条件，记录缺失项。未说明 GPU 驱动版本、CUDA 版本或 `nvidia-smi` 输出的基准测试是不完整的。

### 步骤 3：运行测试
运行一次并观察，再运行第二次和第三次。各次运行间的波动本身就是数据。

### 步骤 4：比较结果

| 情况 | 含义 |
|-----------|--------------|
| 结果在预期方差内匹配主张 | 主张已验证，置信度高 |
| 结果存在显著差异 | 主张可能错误，或条件不同。检查条件后报告差异 |
| 完全无法复现 | 以现有资源无法验证该主张，应标记 |
| 结果优于主张 | 值得关注，可能表示设置不同或原主张较保守 |

### 步骤 5：记录复现过程

```
## 验证

- 测试的主张：[来源中的准确主张]
- 我的结果：[数值]
- 条件：[硬件、软件、标志、方法]
- 多次运行的方差：[N 次运行的最小值/最大值/平均值]
- 结论：已验证 / 部分支持 / 相互矛盾 / 无法验证
- 说明：[测试条件的任何限制]
```

## 无法测试时

有些主张无法以现有资源测试，例如需要价值 1 万美元的云额度、专有硬件或无法访问的系统。此时：

1. **寻找独立复现。**是否有人测试过同一主张？寻找复现实验、社区基准测试或论坛讨论。
2. **批判性阅读方法。**无法亲自测试时，应审计测试方法：样本量是否足够？混杂变量是否受控？是否存在利益冲突？
3. **在草稿中标记未测试主张。**“该基准由供应商完成，尚未经独立验证”是诚实且可保护读者的表述。

## “我亲自搭建过”标准

适用于技术教程和操作指南，例如“在 16GB 消费级 GPU 上运行 350 亿参数 MoE 模型”：

- 文中每个配置标志都必须由作者测试过。
- 文中每条命令都必须产生所述输出。
- 每张截图或终端输出都必须来自作者自己的系统。
- 不说“应该能用”，只说“在这些条件下我验证可用”。
- 配置无效时，应明确说明并解释原因。

这是将具备实证基础的技术写作与泛泛教程区分开的标准。错误和死路本身也是有价值的信息。
