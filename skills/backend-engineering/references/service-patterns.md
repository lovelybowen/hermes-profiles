# 服务模式

## 架构风格

| 风格 | 分离轴 | 最适合场景 | 权衡 |
|-------|----------------|----------|----------|
| 分层 | 技术层（controller → service → repository） | 简单 CRUD 服务、约定优于配置的框架 | 业务逻辑可能跨层泄漏 |
| 整洁架构 | 依赖方向（外层 → 内层） | 复杂业务逻辑、长期项目 | 接口样板代码较多 |
| 六边形（端口与适配器） | 外部与内部（端口作为边界） | 具有多个 I/O 来源的服务 | 前期接口更多 |
| 管线 | 请求按阶段流转 | 数据处理、middleware 较重的服务 | 可组合但难以追踪 |

## 请求生命周期

```
Request → Middleware 1 → Middleware N → Router → Controller → Service → Repository → Database
                                             ↓
                                        Response ← Middleware N ← Middleware 1 ←
```

每层都有明确职责：

| 层级 | 职责 | 不负责 |
|-------|---------------|------------|
| Middleware | 认证、日志、限流、CORS、追踪 | 业务逻辑、数据访问 |
| Controller | 请求解析、验证、响应格式化 | 业务决策、数据库查询 |
| Service | 业务规则、工作流编排、状态管理 | HTTP 关注点、直接数据库访问 |
| Repository | 数据访问、查询构造、结果映射 | 业务规则、请求解析 |

## 后台任务处理

| 模式 | 使用时机 | 关注点 |
|---------|-------------|----------|
| 进程内工作者 | 轻量、无外部依赖 | 内存、进程生命周期、扩展性 |
| 消息队列 | 可靠异步处理 | 队列管理、重试、DLQ |
| 定时 cron | 周期性批处理 | 时间保证、重叠执行 |
| 事件驱动流处理 | 实时事件处理 | 状态管理、顺序 |

每个后台任务都应具备幂等性、可重试性和明确的失败路径，例如死信或告警。
