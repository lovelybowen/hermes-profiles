# 系统化调试

> **溯源：** 本技能是 Hermes 自带技能 `software-development/systematic-debugging` 的本地化版本（同一方法论，中文表述，含量有限的适配），随仓库分发以固定版本。**上游更新不会自动回流**——升级 Hermes 后需人工比对并在此同步，以免与自带技能产生无法察觉的漂移。
>
> **适用范围：** 面向服务端 / Web / CLI 的软件缺陷。其中 macOS 桌面应用排障属上游携带的通用内容，仅在缺陷确实发生在 macOS 桌面应用时适用，见 `references/macos-desktop-troubleshooting.md`。

## 概述

随意修复既浪费时间，又会制造新缺陷。快速补丁会掩盖底层问题。

**核心原则：**尝试修复前始终先找到根因。只修复症状就是失败。

## 与 `debugging-methodology` 的关系

本技能是**根因协议的权威细则**（四阶段：根因调查 → 模式分析 → 假设与测试 → 实施），由 `debugger` 角色加载。

`debugging-methodology` 提供工程过程索引（复现 → 隔离 → 根因 → 修复 → 验证）以及复现清单、隔离技巧、性能调试等参考资料。**进入根因阶段后以本技能为准**；需要复现或隔离的具体技巧时，加载 `debugging-methodology` 的对应参考文件。

## 铁律

```
未先调查根因，不得实施修复
```

未完成阶段 1，就不能提出修复方案。

## 使用时机

适用于任何技术问题：
- 测试失败。
- 生产缺陷。
- 异常行为。
- 性能问题。
- 构建失败。
- 集成问题。

**尤其适用于：**
- 时间紧迫，紧急情况容易诱使人猜测。
- “只快速修一下”看似显而易见。
- 已经尝试多种修复。
- 上一次修复无效。
- 尚未完全理解问题。

**以下情况也不能跳过：**
- 问题看似简单，简单缺陷同样存在根因。
- 正在赶时间，仓促行动必然造成返工。
- 有人要求立即修复，系统化方法比反复乱试更快。

## 四个阶段

完成当前阶段后才能进入下一阶段。

## 阶段 1：根因调查

**在尝试任何修复之前：**

### 1. 仔细阅读错误信息

- 不要跳过错误或警告，它们经常包含准确的解决线索。
- 完整阅读堆栈跟踪，记录行号、文件路径和错误码。
- **操作：**读取错误位置对应的源文件，并在代码库中搜索错误字符串，找到所有相关代码路径。

### 2. 稳定复现

- 能否可靠触发？准确步骤是什么？
- 如果无法复现 → 收集更多数据，不要猜测。
- **操作：**运行失败测试或触发缺陷：

```bash
pytest tests/test_module.py::test_name -v --tb=long
```

### 3. 检查近期变更

- 哪些变更可能导致此问题？检查 Git 差异、近期提交、新依赖和配置变更。
- **操作：**

```bash
git log --oneline -10
git diff
git log -p --follow src/problematic_file.py | head -100
```

### 4. 在多组件系统中收集证据

**当系统包含多个组件时，例如 API → 服务 → 数据库、CI → 构建 → 部署：**

提出修复前先增加诊断埋点。针对每个组件边界：
- 记录进入组件的数据。
- 记录离开组件的数据。
- 验证环境或配置是否正确传播。
- 检查每一层的状态。

运行一次以收集能够表明故障发生位置的证据，然后分析并识别失败组件。

### 5a. 检查模式与环境差异

**当缺陷可在生产环境复现、但无法在测试中复现时：**

1. 使用 `PRAGMA table_info()`、`\\.schema` 或等效命令比较测试夹具模式与生产模式。
2. 查找缺失的 `NOT NULL` 列、外键、唯一约束或默认值。
3. 检查 SQLite 日志模式、连接标志或 PRAGMA 设置的差异。
4. 验证测试数据与生产数据形态一致，不仅比较列名，还要比较约束。

简化的测试模式是隐藏缺陷的常见来源。如果生产表包含 `model TEXT NOT NULL`，而测试表只有 `vector BLOB`，仅在违反 `NOT NULL` 时触发的缺陷就会顺利通过测试。

**操作：**分别对两个数据库运行 `PRAGMA table_info(table_name)`，并比较输出。

### 5b. 检查回退链中的异常类型精确性

**当 `try/except` 回退未捕获日志中的错误时：**

```python
try:
    # 主路径，可能抛出 OperationalError
    conn.execute("INSERT INTO t (model_name) VALUES (?)", ...)
except sqlite3.OperationalError:
    # 回退路径，可能抛出 IntegrityError（同级类而非子类）
    conn.execute("INSERT INTO t (vector) VALUES (?)", ...)
```

`OperationalError` 和 `IntegrityError` 是**同级类**，二者都继承自 `DatabaseError`，后者继承自 `Error`。捕获其中一个并不会捕获另一个。

可采用以下修复方式：
- 如果两条路径可能以不同子类型失败，捕获父类（`except sqlite3.DatabaseError`）。
- 作为最后手段捕获 `Exception`，范围更广，但比留下缺口更安全。
- 显式处理每个预期异常类型。

### 5c. 渐进式特征刻画 - 工具与 API 行为

**当检索系统、API 或知识图谱返回空结果或不一致结果时：**

从有效场景开始逐步扩展，直到出现故障，从而隔离导致失败的变量。

| 输入 | 预期结果 | 实际结果 | 诊断 |
|-------|----------|--------|-----------|
| 单个已知术语，例如 `python` | 有结果 | 有结果 | 工具有效，连接正常 |
| 同一文档中的双词短语（`type safety`） | 有结果 | 有结果 | 短语检索有效 |
| 相关双词短语（`generic types`） | 有结果 | 0 条 | **发现边界**，问题与具体短语有关 |
| 包含相同术语的更长查询 | 0 条 | 0 条 | 确认并非偶发现象 |

**不要跳过特征刻画：**直接断言“嵌入模型坏了”只是猜测。该表格会逐一排除变量。

### 5d. 修复库代码前检查依赖来源

**当缺陷追踪到第三方依赖时：**

修改库代码前，先确认其安装来源：

```bash
pip show <package-name>
```

关键字段：
- **可编辑项目位置：**如果存在，说明这是通过 `pip install -e` 安装的开发副本。是否有意为之？
- **位置：**位于 `site-packages`（生产）还是临时或开发目录？
- **版本：**通过 `pip index versions <package-name>` 与 PyPI 最新版本比较。

**规则：**如果软件包以可编辑开发副本安装，而你并未有意这样做，应停止并询问。症状可能源于代码偏离上游；正确做法是切换到生产软件包，而不是修改分支副本。

**示例：**后台工作进程因 `table X has no column named Y` 崩溃。调查发现依赖来自 `/private/tmp/some-fork/` 中的可编辑安装。开发分支在 INSERT 语句中增加了列名，却没有添加模式迁移。正确修复不是为该分支补迁移，而是切换到生产 PyPI 软件包并删除开发副本。

### 6a. 猜测之前先研究 - 系统化 Web 搜索

**当已经收集所有本地证据，却仍然不理解根因时：**

不要猜测解决方案，应开展结构化 Web 研究：

1. **搜索准确错误信息：**引用错误，包含错误码和函数名。
2. **搜索症状和平台上下文：**组合故障内容与操作系统或工具版本。
3. **搜索组件或服务名称：**XPC 服务、守护进程和子系统通常已有缺陷记录。
4. **优先查看近期讨论：**筛选当前版本，旧解决方案可能不再适用。
5. **提出方案前阅读完整讨论：**只读部分内容会产生不完整修复。
6. **检查经过确认的变通方案：**查看讨论结尾，不要只看最初诊断。

### 6b. macOS 应用故障排查 - 沙箱应用

**仅当缺陷发生在 macOS 桌面应用时适用**；服务端 / Web / CLI 缺陷跳过本步骤。
完整流程见 `references/macos-desktop-troubleshooting.md`，示例见 `references/macos-sandbox-debug-example.md`。

### 6c. 跟踪数据流

**当错误发生在调用栈深处时：**

- 错误值来自哪里？
- 谁使用错误值调用了这个函数？
- 持续向上游追踪，直到找到来源。
- 在来源处修复，而不是在症状处修补。

**操作：**在代码库中搜索函数引用和变量赋值，以追踪数据路径。

### 阶段 1 完成检查清单

- [ ] 已完整阅读并理解错误信息。
- [ ] 问题可以稳定复现。
- [ ] 已识别并评审近期变更。
- [ ] 已收集证据，包括日志、状态和数据流。
- [ ] 已将问题隔离到具体组件或代码。
- [ ] 已形成根因假设。

**停止：**在理解问题为何发生之前，不得进入阶段 2。

## 阶段 2：模式分析

**修复前先找到模式：**

### 1. 查找有效示例

- 在同一代码库中找到正常工作的相似代码。
- 哪些正常代码与故障代码相似？

### 2. 与参考实现比较

- 如果正在实现某种模式，应完整阅读参考实现，不要略读。
- 应用前充分理解该模式。

### 3. 识别差异

- 正常实现和故障实现之间有何不同？
- 列出每项差异，无论多小。
- 不要假设“这不可能有影响”。
- **操作：**在代码库中搜索相似模式进行比较。

### 4. 理解依赖

- 它还需要哪些组件？
- 需要哪些设置、配置和环境？
- 它建立在哪些假设上？

---

## 阶段 3：假设与测试

**科学方法：**

### 1. 提出单一假设

- 清楚陈述：“我认为 X 是根因，因为 Y”。
- 把它写下来，内容要具体，不要含糊。

### 2. 最小化测试

- 通过尽可能小的变更检验假设。
- 每次只改变一个变量。
- 不要同时修复多个问题。

### 3. 继续之前先验证

- 有效？→ 进入阶段 4。
- 无效？→ 提出新假设。
- 不要在原方案上继续叠加修复。

### 4. 不知道时

- 明确说“我不理解 X”，不要假装知道。
- 寻求帮助并开展更多研究。

---

## 阶段 4：实施

**修复根因，而不是症状：**

### 1. 创建失败测试用例

- 使用尽可能简单的复现方式，条件允许时编写自动化测试。
- 修复前必须具备失败用例。
- 测试环境必须反映生产环境，对照真实模式审计测试夹具。

### 2. 实施单一修复

- 处理已经识别的根因，每次只做一项变更。
- 不做“既然已经在这里就顺便改”的改进，也不捆绑重构。

### 3. 验证修复

```bash
# 运行特定回归测试
pytest tests/test_module.py::test_name -v

# 运行完整测试套件，确认无回归
pytest tests/ -q
```

### 4. 修复无效时 - 三次规则

- **停止。**
- 统计已经尝试了多少次修复。
- 如果少于 3 次：带着新信息返回阶段 1 重新分析。
- **如果达到或超过 3 次：停止并质疑架构，参见下面的步骤 5。**
- 未经架构讨论，不得尝试第 4 次修复。

### 5. 三次以上修复失败：质疑架构

**表明存在架构问题的模式：**
- 每次修复都在不同位置暴露新的共享状态或耦合。
- 修复需要进行“大规模重构”。
- 每次修复都会在其他位置产生新症状。

**停下来质疑基本设计：**
- 这个模式从根本上是否合理？
- 是否只是“出于惯性继续坚持”？
- 应该重构架构，还是继续修复症状？

**继续修复前必须讨论。**这不是假设失败，而是架构错误。

## 危险信号 - 停止并遵循流程

如果发现自己正在这样想：
- “现在先快速修，之后再调查。”
- “先改一下 X 看看是否有效。”
- “同时增加多项变更，再运行测试。”
- “跳过测试，我手工验证。”
- “大概是 X，我先修它。”
- “我没有完全理解，但这样也许有效。”
- “主要问题如下：[未经调查直接列出修复项]。”
- 尚未追踪数据流就提出解决方案。
- **已经尝试两次以上，仍想“再试一次修复”。**
- **每次修复都在不同位置暴露新问题。**

**出现任何一种情况都意味着：停止，返回阶段 1。**

**如果三次以上修复失败：**质疑架构，参见阶段 4 的步骤 5。

## 调查流程 - 保持推进

调查仍在进行，而用户表示“有进展，但还没完成”时：

不要用澄清问题打断流程。继续推进：收集更多证据、尝试下一项诊断步骤、检查其他角度。暂停调查并询问“你尝试 X 后发生了什么？”会浪费用户注意力。

**应继续推进的信号：**
- “有进展，但还没完成” → 继续调查。
- 用户忽略澄清问题 → 他们需要行动，而不是更多问题。
- “好”或“还是坏的” → 尝试下一步，不要请求许可。

**替代做法：**从日志、数据库或文件状态中推导信息，不要让用户充当你的诊断埋点。只有确实无法在没有输入的情况下继续，并且已经穷尽所有自主手段时，才能提问。

## 常见借口

| 借口 | 事实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单问题同样存在根因，而且该流程处理简单缺陷也很快。 |
| “情况紧急，没时间走流程” | 系统化调试比猜测和反复试错更快。 |
| “先试一下这个，再调查” | 第一次修复会确立后续模式，应从一开始就正确处理。 |
| “确认修复有效后再写测试” | 未经测试的修复无法持久；先有测试才能证明修复。 |
| “同时做多个修复更省时间” | 这样无法隔离哪项变更有效，并且会制造新缺陷。 |
| “我看出问题了，直接修” | 看到症状不等于理解根因。 |
| 两次以上失败后仍想“再试一次” | 三次以上失败意味着可能存在架构问题，应质疑当前模式。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据、追踪数据流 | 理解发生了什么以及为什么发生 |
| **2. 模式** | 查找有效示例、比较并识别差异 | 了解具体差异 |
| **3. 假设** | 提出理论、最小化测试、每次改变一个变量 | 假设得到确认或形成新假设 |
| **4. 实施** | 创建回归测试、修复根因并验证 | 缺陷解决，全部测试通过 |
