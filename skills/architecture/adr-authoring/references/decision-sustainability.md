# 决策可持续性框架

用于评估架构决策记录（ADR）能否经受现实检验的框架。基于 InfoQ 文章“可持续的架构设计决策”，并记录在 ADR 社区仓库中。

**概念来源：**https://www.infoq.com/articles/sustainable-architectural-design-decisions/；ADR 社区仓库中也提供 `locales/en/documents/decision-sustainability-criteria/` 和 `locales/en/documents/guidelines-to-achieve-sustainable-decisions/`。

## 五项可持续性标准

每份 ADR 在接受前都应根据这些标准评估。它们构成 ADR 评审流程的质量门检查清单。

### 1. 战略性

**问题：**此决策是否考虑长期影响？

战略性决策考虑未来运行、维护和演进，而不只解决眼前问题。它会明确说明此选择的下游后果。

**检查清单：**
- [ ] 此决策的预期生命周期是什么？6 个月、2 年还是 10 年？
- [ ] 此决策将如何影响未来维护负担？
- [ ] 此决策是否将团队锁定在特定技术或模式？
- [ ] 是否记录了切换成本？

**陷阱：**以未来 6 至 12 个月为代价来优化今天的决策仍可能正确，但必须在依据中明确短期时间范围。

### 2. 可衡量且可管理

**问题：**此决策能否随时间被客观评估？

可持续决策具有可衡量结果。六个月后应能回看并判断决策是否正确。

**检查清单：**
- [ ] 是否定义成功或失败标准？
- [ ] 在可能处是否指定数值目标？例如延迟 p99 < 200ms、成本 < $500/月。
- [ ] 决策粒度是否足以追溯？过细会造成噪声，过粗会产生歧义。
- [ ] 是否记录此决策与其他决策间的依赖关系？

**陷阱：**“提升性能”不可衡量，“将 p99 延迟从 800ms 降至 200ms 以下”才可衡量。质量属性场景，即 arc42 中的场景，是正确工具。

### 3. 可实现且现实

**问题：**这是“足够好”的选择，而非追求完美的选择吗？

可持续决策建立在团队实际能够交付的基础上。为假想未来需求过度设计是常见失败模式。

**检查清单：**
- [ ] 团队基于当前技能和能力能否实现？
- [ ] 此决策是否避免过度设计？是否考虑过更简单替代方案并以文档说明拒绝理由？
- [ ] 实施时间线是否现实？
- [ ] 运行成本是否在预算内？

**陷阱：**团队无法执行的技术优雅决策是架构失败，而非团队失败。“足够好”测试是：此决策是否以 20% 的复杂度获得 80% 的收益？

### 4. 植根于需求

**问题：**此决策是否可追溯到真实业务或技术需求？

可持续决策基于真实问题，即公司背景、团队构成和用户需求，而不是抽象的“最佳实践”。

**检查清单：**
- [ ] 此决策是否直接关联具体需求或约束？
- [ ] 是否考虑团队技能、培训预算和组织背景？
- [ ] 若需求改变，是否需要重新评估此决策？如需要，应标记。
- [ ] 是否记录外部依赖，例如供应商、平台和法规？

**陷阱：**“每个人都用 Kubernetes”不是需求；“当前单服务器架构无法处理可预测流量模式，因此需要水平扩展”才是需求。建立在从众效应而非真实需求上的决策很快会过时。

### 5. 持久性

**问题：**此决策是否建立在短期内不太会过时的知识之上？

可持续决策优先采用持久知识而非流行技术。与平台无关的模式和架构策略比具体工具更长久。

**检查清单：**
- [ ] 决策是否基于架构模式或策略，而非具体工具版本？
- [ ] 选定的供应商或产品明天消失时，架构是否仍能存续？
- [ ] 底层技术选择改变时，决策依据是否仍有效？
- [ ] ADR 是否区分“是什么”，即模式，和“用哪个”，即具体工具？

**示例：**因为“我们需要审计轨迹”而选择事件溯源，是具有持久性的架构决策；因为“Kafka 很流行”而选择事件溯源则不是。ADR 应阐明持久原则，而不只是工具选择。

## 八条可持续决策准则

以下准则来自 InfoQ 文章，用于将标准落实到实践：

| # | 准则 | 适用内容 |
|---|-----------|-----------|
| 1 | **初始文档采用精简方式。**第一天不要写 Tyree & Akerman，先从 Nygard 或 MADR 开始。 | ADR 起草 |
| 2 | **先确定并记录所有重要决策。**展开细节前先识别真正重要的事项。 | ADR 识别 |
| 3 | **初步批准后再补充重要决策细节。**利益相关方确认方向正确后再使用完整模板。 | ADR 评审 |
| 4 | **琐碎决策使用精简版本。**并非每个决策都需要选项分析。明显选择使用索引中的一段文字或 Nygard ADR 即可。 | 模板选择 |
| 5 | **复用既有架构知识。**不要重新发明 arc42、Martin Fowler 或自身历史 ADR 已记录的模式，应引用它们。 | ADR 编写 |
| 6 | **建立决策、需求和代码之间的可追溯链接。**每份 ADR 都应向后链接驱动它的需求，并向前链接实现它的代码。 | ADR 结构 |
| 7 | **为可追溯链接提供自动一致性检查。**如何实现机械化检查见 `references/fitness-functions.md`。 | CI/治理 |
| 8 | **强制要求决策依据。**依据是 ADR 最重要的部分；没有依据的决策不是决策，而是观点。 | ADR 质量 |

## 使用框架：ADR 评审检查清单

接受 ADR 前，根据以下问题进行评估：

```
1. 战略性：是否考虑超出眼前问题的长期影响？
   如果否：在 ADR 中增加“未来考量”章节。

2. 可衡量性：是否定义成功/失败标准，最好有数值目标？
   如果否：接受前增加质量属性场景。

3. 可实现性：这是否“足够好”，而非为假想未来过度设计？
   如果否：记录考虑过哪些更简单的替代方案，以及为什么当前额外复杂度合理。

4. 需求根基：是否能追溯到具体需求、约束或团队背景？
   如果否：识别真实需求并建立链接；如不存在，应重新评估是否需要该决策。

5. 持久性：依据是否基于持久架构知识，而非今天的潮流？
   如果否：重构 ADR，使其阐明架构原则而不是具体工具名。
```
