# C4 各层级：目的、受众、建模内容与易错点

C4 是一个**缩放层级**模型，不是四种不同的图。每层回答不同读者的问题，越往下细节越多、读者越窄。

## 第 1 层：系统上下文（System Context）

| 维度 | 内容 |
|---|---|
| 目的 | 说明这个系统是什么、它服务于谁、与哪些外部系统交互 |
| 受众 | 所有人，包括非技术人员、业务方、新成员 |
| 建模内容 | 目标系统（一个框）、使用者/角色、其他外部系统；不含内部结构、不含技术选型 |
| 主要失败模式 | 把内部模块画进上下文图 |

**易错点：**

- **把技术写进去。** 上下文图里出现「Redis」「Kafka」说明你画错了层级——那些属于容器层。
- **边界不清。** 目标系统必须有唯一的框；如果画了两个平级系统，读者无法判断谁在范围内。
- **省略外部系统。** 漏掉支付网关、身份提供方、邮件服务，会让后续的失败模式分析失去输入。
- **面向组织而非软件。** C4 描述的是软件系统边界，不是部门边界。

## 第 2 层：容器（Container）

| 维度 | 内容 |
|---|---|
| 目的 | 展示系统由哪些可独立部署/运行的单元组成，以及它们如何通信 |
| 受众 | 开发者、运维、集成人员 |
| 建模内容 | Web 应用、API、服务、数据库、消息队列、文件存储；每个容器标注技术选型与职责；容器间的同步/异步关系 |
| 主要失败模式 | 用「层」代替容器，把图变成分层架构图 |

**易错点：**

- **容器 ≠ 类库或模块。** 容器是运行单元，有独立的部署与生命周期。一个进程内的子模块不是容器。
- **忘标注技术。** `[API]` 不如 `[API<br/>Go, gRPC]` 有用；技术选型是这一层的核心信息。
- **把数据库画成唯一存储。** 若系统有缓存、对象存储、搜索索引，它们各自是容器。
- **漏掉异步路径。** 只画同步调用会掩盖队列表、事件总线带来的失败模式与延迟。
- **共享数据库不画。** 两个服务共用一个库时必须显式画出，它是最常见的耦合来源。

## 第 3 层：组件（Component）

| 维度 | 内容 |
|---|---|
| 目的 | 打开一个容器，说明它内部由哪些组件构成、各自职责与接口 |
| 受众 | 该容器的开发者、评审者 |
| 建模内容 | 容器内的逻辑模块、它们的职责、通过接口的协作关系、与外部容器/存储的交互 |
| 主要失败模式 | 逐层打开所有容器，产出大量无人维护的图 |

**易错点：**

- **不要为每个容器都画组件图。** 只为需要拆分工作、存在争议或失败模式复杂的容器画。
- **组件不是文件、不是类。** 组件是「有明确职责与接口的一组代码」，粒度通常对应一个包或几个协作模块。
- **省略接口。** 没有接口说明的组件图无法用于契约设计。
- **忽略与容器的边界。** 组件图必须标出哪些框是外部容器或存储，否则读者会误以为它们也属于本容器。

## 第 4 层：代码（Code）

| 维度 | 内容 |
|---|---|
| 目的 | 说明一个组件内部如何实现，通常用于解释关键设计模式或复杂算法 |
| 受众 | 实现该组件的开发者 |
| 建模内容 | 类、接口、关键关系；必须与代码同步，通常由工具生成 |
| 主要失败模式 | 手工维护，迅速过时并开始误导 |

**易错点：**

- **手工维护代码图。** 代码层图应当由工具（Structurizr、IDE、UML 反向工程）从源码生成，否则必然与实现漂移。
- **过度使用。** 大多数情况下代码本身就是最好的「代码图」；只在需要解释复杂协作或模式时才画。
- **当成文档主体。** 代码层是金字塔的 L3 档案，只在按需深挖时阅读，不应进入主交付物。

## 层级选择速查

| 问题 | 应看的层级 |
|---|---|
| 这个系统做什么、和谁交互？ | 第 1 层 |
| 由哪些可部署单元组成、怎么通信？ | 第 2 层 |
| 某个容器内部怎么组织？ | 第 3 层 |
| 某个关键模式怎么实现？ | 第 4 层 |
