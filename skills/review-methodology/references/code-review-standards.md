# 代码评审标准

基于 Google 工程实践，为 Hermes 代码库和 Magnus 的 Python/JS/Go 项目调整。

> **先按档位定深度，再按九维度评审。** 本文件的九个维度是评审**内容**的清单；评审**深度**由交接的 `evidence_level`（`L0` / `L1` / `L1+L2` / `Full`）决定。开始逐维度评估前，先读 `references/evidence-level-verification.md` 选定本档的核验范围与抽样要求。

## 九个维度

每次代码评审均按以下优先级评估这些维度。

### 1. 设计 - 最关键的方面

**检查内容：**
- 整体设计是否适合该问题？
- 组件之间的交互是否良好？
- 变更应留在当前代码库，还是应作为独立库？
- 是否能良好集成到现有系统？
- 现在是否是增加此功能的合适时机？

**危险信号：**
- 设计解决尚不存在的问题，即增加复杂度的“面向未来”设计。
- 设计重复现有功能。
- 现有约定可用时，设计引入新模式。
- 设计耦合本应独立的组件。

### 2. 功能性 - 是否真正有效？

**检查内容：**
- 变更是否实现了其声明意图？先阅读 Issue 或说明。
- 该意图是否对用户有益，包括终端用户和未来开发者？
- **边界情况：**空输入、空值、网络失败、并发访问时会发生什么？
- **错误处理：**错误是否在正确层级捕获？可恢复还是致命？
- **并发：**死锁、竞态条件、线程安全。

**危险信号：**
- 使用 `except: pass` 吞掉错误信息。
- 没有处理明显边界情况，例如空列表、缺失键、类型不匹配。
- 并发模型易产生竞态条件，例如没有锁的共享可变状态。

### 3. 复杂度 - 是否比必要程度更复杂？

**在每个层级检查内容**，包括代码行、函数、类和模块：
- 没见过此代码的人能否快速理解？
- 未来开发者调用或修改时是否容易引入缺陷？
- 方案是否为可用的最简单方案，还是过度设计？

**过度设计信号：**
- 只有一个实现的抽象接口，违反 YAGNI。
- 为尚不存在的情况提供可配置性。
- 简单方案可用时仍应用通用模式。
- 单个函数足以胜任时建立继承层级。

**规则：**解决当前已知需要解决的问题，而不是推测未来可能需要解决的问题。

### 4. 测试 - 变更是否可验证？

**检查内容：**
- 为变更选择合适的单元、集成或 E2E 测试。
- 测试应与生产代码位于同一 CL，紧急情况除外。
- **代码损坏时测试是否确实失败？**为已知失败模式编写正向测试。
- **测试是否会产生误报？**警惕因无关变更而失败的脆弱测试。
- 断言是否简单且有意义？
- 不同测试方法之间是否充分隔离？

**危险信号：**
- 测试从不运行，例如没有 CI 集成或被跳过。
- 测试断言了错误内容，即测试实现而非行为。
- 测试比被测代码更复杂。
- 缺陷修复没有测试，缺少回归覆盖。

### 5. 命名 - 仅从名称能否理解意图？

**检查内容：**
- 名称是否传达存在的*原因*，而不仅是*是什么*？
- 名称是否简洁且不晦涩？
- 函数名是否描述其行为，采用动词加对象模式？
- 变量名是否描述内容而非类型？

**危险信号：**
- 在循环外使用单字母变量。
- 名称与代码实际行为不符。
- 使用项目中不标准的缩写。
- 在 Python/JS 中使用匈牙利命名法。

### 6. 注释 - 解释为什么，而不只是做什么

**检查内容：**
- 注释解释代码存在的*原因*，而非它做了*什么*，代码本身应具备自说明性。
- 例外包括复杂正则表达式和逻辑不明显的算法。
- 注释包含代码本身无法表达的信息，例如设计依据和权衡。
- TODO 注释应有关联 Issue 或明确负责人。
- 不保留被注释掉的代码。

**危险信号：**
- 类似 `# This line adds 1 to x` 的注释，只是在陈述显而易见的内容。
- 对 reviewer 会质疑的不明显决策没有注释。
- 旧注释与代码当前行为不符，形成过时文档。

### 7. 风格 - 约定很重要

**检查内容：**
- 遵守项目风格指南，如存在。Python 使用 PEP 8；Hermes 使用 ruff 配置。
- 相比个人偏好，优先采用项目既有模式。
- 非阻断风格建议使用 “Nit:” 前缀。
- 仅风格变更应与功能变更分置不同 CL。

**危险信号：**
- 在包含逻辑变更的同一 PR 中重新格式化整个文件。
- 同一文件或模块内部风格不一致。

### 8. 一致性 - 代码库应像出自同一人之手

**检查内容：**
- 此变更是否遵循邻近代码建立的模式？
- 若既有模式违反风格指南，应优先风格指南。
- 如无风格指南规则和既有模式，应遵循语言的标准惯用法。

**危险信号：**
- 新代码采用与既有同类代码不同的方法。
- 导入风格与项目其余部分不同。
- 错误处理模式与代码库其余部分不同。

### 9. 文档 - 变更是否更新文档？

**检查内容：**
- CL 变更构建、测试、部署或发布流程时，文档是否更新？
- CL 变更 API 行为时，文档是否更新？
- CL 新增或修改 CLI 标志时，帮助文本和示例是否更新？
- 代码删除时，相关文档是否移除？

## 严重程度等级

| 严重程度 | 标签 | 含义 | 行动 |
|----------|-------|---------|--------|
| 🔴 严重 | `blocking` | 缺陷、安全问题或正确性问题 | 合并前必须修复 |
| 🟡 警告 | `should-fix` | 设计问题、测试缺口、复杂度关注点 | 应修复，但可讨论 |
| 💡 建议 | `nit` | 风格偏好、轻微改进 | 可忽略，但应考虑 |
| ❓ 问题 | `question` | 不理解此代码路径 | 作者应澄清 |

## Magnus 专用约定

这些约定叠加在上述通用标准之上：

- **面向用户文本中的破折号：**不允许使用，应标为阻断问题。
- **没有日志的 `except Exception`：**标为 `should-fix`，静默失败是调试噩梦。
- **没有异常类型的裸 `except:`：**标为严重问题，它会捕获 `KeyboardInterrupt` 和 `SystemExit`。
- **硬编码路径**，例如 `/Users/magnus/`、`/home/` 或绝对路径：标为阻断问题，无法在其他机器上运行。
- **代码中的 API 密钥或令牌：**标为严重问题，这是凭据泄露。
- **HTML 模板中的内联 `color`/`background-color` 样式：**标为 `should-fix`，会产生深色模式残留。
- **没有断言的测试：**标为 `should-fix`，属于无效测试。
- **新公共函数缺少类型提示：**标为建议，Magnus 偏好带类型的 Python。
