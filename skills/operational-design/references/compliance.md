# 合规与审计框架

合规是一个系统，而不是一个项目。它需要嵌入式控制、持续监控和定期测试。以下框架涵盖 SaaS 和技术公司最常见的合规制度。

## SOC 2

SOC 2（System and Organization Controls 2，系统与组织控制 2）是 SaaS 公司最常见的合规框架。它报告与安全性、可用性、处理完整性、保密性和隐私相关的控制。

### 信任服务准则（TSC）

| 类别 | 准则 | 覆盖内容 |
|----------|----------|---------------|
| **安全性** | CC1-CC9 | 保护系统免受未经授权的访问。所有组织都必须满足的基础准则。 |
| **可用性** | A1 | 系统按照承诺或约定可供运行和使用。 |
| **处理完整性** | PI1 | 系统处理完整、有效、准确、及时且经过授权。 |
| **保密性** | C1 | 被指定为机密的信息受到保护。 |
| **隐私** | P1-P4 | 个人信息的收集、使用、保留、披露和处置符合承诺。 |

### SOC 2 报告类型

| 类型 | 说明 | 适用时机 |
|------|-------------|----------------|
| **Type I** | 控制在某一时点设计得当 | 首次审计、刚开始实施 |
| **Type II** | 控制在一段期间内有效运行（通常为 6-12 个月） | 客户要求、供应商尽职调查 |

### 各领域关键控制

**安全性（CC1-CC9）：**
- 访问控制政策与执行
- 逻辑访问复审（每季度）
- 变更管理流程
- 事件响应计划与测试
- 供应商风险管理
- 静态和传输中加密
- 物理安全（办公室/数据中心）
- 监控和告警
- 背景调查
- 安全意识培训

**可用性（A1）：**
- 可用时间 SLA 和监控
- 业务连续性/灾难恢复计划
- 备份与恢复测试
- 容量规划

**处理完整性（PI1）：**
- 输入验证控制
- 错误处理和纠正措施
- 批处理作业监控

**保密性（C1）：**
- 数据分类政策
- 机密数据访问限制
- 数据保留与处置

### SOC 2 就绪检查清单

| 阶段 | 活动 | 时间线 |
|-------|-----------|----------|
| **范围界定** | 定义系统边界，识别范围内的服务和数据 | 2-4 周 |
| **风险评估** | 识别 TSC 准则相关风险，记录控制目标 | 2-4 周 |
| **控制设计** | 记录现有控制，为缺口设计新控制 | 4-8 周 |
| **控制实施** | 构建和部署控制，更新政策 | 4-12 周 |
| **证据收集** | 运行控制，收集审计证据 | 3-6 个月（Type II） |
| **审计** | 外部审计师复核控制和证据 | 4-8 周 |

## ISO 27001

信息安全管理体系（ISMS）的国际标准。其范围比 SOC 2 更广——它要求建立管理体系，而不只是控制。

### ISO 27001 方法

| 组成部分 | 说明 |
|-----------|-------------|
| **ISMS** | 管理敏感信息的系统方法 |
| **附录 A 控制** | 跨 4 个领域（组织、人员、物理、技术）的 93 项控制 |
| **PDCA 循环** | Plan-Do-Check-Act 持续改进 |
| **风险评估** | 基于风险的方法——根据风险而非检查清单选择控制 |
| **适用性声明** | 哪些附录 A 控制适用，以及原因 |

### ISO 27001 与 SOC 2 对比

| 维度 | SOC 2 | ISO 27001 |
|-----------|-------|-----------|
| 重点 | 控制有效性 | 管理体系 |
| 灵活性 | 固定 TSC 准则 | 基于风险，自主选择控制 |
| 认证 | 审计师意见书 | 颁发证书 |
| 认可范围 | 以美国为主 | 国际 |
| 续期 | 每年 | 三年认证 + 监督审计 |

### 关键要求

1. **ISMS 范围**——包含和排除哪些内容，并说明理由
2. **信息安全政策**——每年复审的顶层政策
3. **风险评估**——系统化风险评估方法论
4. **风险处置计划**——如何处理风险
5. **内部审计**——定期对 ISMS 进行内部审计
6. **管理评审**——最高管理层复审 ISMS 表现
7. **持续改进**——跟踪并解决不符合项

## GDPR 就绪

《通用数据保护条例》规范如何处理欧盟居民的个人数据，无论公司位于何处。

### 关键原则

| 原则 | 要求 |
|-----------|-------------|
| **合法、公平、透明** | 处理具有法律依据，隐私声明清晰 |
| **目的限制** | 仅为指定的明确目的收集数据 |
| **数据最小化** | 只收集必要数据 |
| **准确性** | 保持数据准确且及时更新 |
| **存储限制** | 不再需要时删除数据 |
| **完整性和保密性** | 采取适当的安全措施 |
| **问责** | 证明合规（文档、DPO、记录） |

### 数据主体权利

| 权利 | 说明 | 响应时间 |
|-------|-------------|---------------|
| **知情权** | 在收集点提供隐私声明 | 收集时 |
| **访问权** | 个人可以请求其数据 | 30 天 |
| **更正权** | 更正不准确的数据 | 30 天 |
| **删除权**（“被遗忘权”） | 删除个人数据 | 30 天 |
| **限制处理权** | 限制数据使用方式 | 30 天 |
| **数据可携带权** | 以机器可读格式导出数据 | 30 天 |
| **反对权** | 选择退出处理（包括营销） | 随时 |
| **与自动化决策相关的权利** | 获得基于算法的决策说明 | 提出请求时 |

### GDPR 合规路线图

| 阶段 | 活动 | 时间线 |
|-------|-----------|----------|
| **发现** | 数据映射，识别所有个人数据处理 | 4-8 周 |
| **缺口分析** | 比较当前状态与 GDPR 要求 | 2-4 周 |
| **整改** | 更新政策、实施控制、更新合同 | 8-16 周 |
| **实施** | 任命 DPO、发布隐私声明、管理同意 | 4-8 周 |
| **持续运营** | DSAR 处理流程、泄露通知程序、年度复审 | 持续 |

### GDPR 泄露通知

```
根据 GDPR，组织必须在知悉泄露后的 72 小时内
向监管机构报告。

如果泄露可能给个人带来高风险，
还必须在没有不当延迟的情况下通知相关个人。
```

## 常见合规陷阱

| 陷阱 | 症状 | 修正方式 |
|---------|---------|-----|
| **一次性合规，而非持续合规** | 控制在两次审计之间逐渐失效 | 建立持续监控，自动收集证据 |
| **只有文档，没有实施** | 政策存在但未得到遵守 | 测试控制，而不只是文档 |
| **范围蔓延** | 试图一次覆盖所有内容 | 从较窄范围开始，逐步扩展 |
| **缺少高管所有权** | 合规被委派给 IT，却没有业务支持 | 指定高管发起人，在董事会层面报告合规 |
| **供应商盲区** | 供应商可访问数据，但未经合规验证 | 建立供应商风险管理计划，复核合同 |
| **过度依赖自动化** | 用工具取代思考 | 自动化支撑控制，但不能取代判断 |

### 证据收集策略

| 证据类型 | 示例 | 收集方式 |
|---------------|----------|-------------------|
| **系统日志** | 访问日志、变更日志、审计跟踪 | 自动化日志聚合 |
| **配置** | IAM 政策、加密设置 | 基础设施即代码、CI/CD |
| **流程产物** | 已签署表单、获批变更请求 | 文档管理系统 |
| **培训记录** | 已完成的安全培训 | LMS 报告 |
| **复核证据** | 访问复核签字记录 | 每季度自动化工作流 |
| **测试结果** | 渗透测试报告、DR 测试结果 | 定期外部测试 |
