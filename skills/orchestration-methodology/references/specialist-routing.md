# 专家路由

## 路由规则

面对同一组专家，不同的协作顺序会产生完全不同的结果。

## 路由模式

| 模式 | 顺序 | 使用时机 |
|---------|-------|----------|
| **调查 → 决策** | 研究员 → 技术架构师 → 人类责任人 | 外部证据和技术约束齐备后仍需业务、交付或风险裁决 |
| **基线 → 构建** | 编排者 → 条件性研究/架构分析 → QA 设计验证 → 按拓扑调用工程师 → QA 执行 → 评审员 → 人类批准 | 按已确认需求基线交付可验证变更 |
| **诊断 → 预防** | 调试工程师 → QA 工程师 → 评审员 | 故障需要根因、回归覆盖和独立质量门 |
| **探索 → 收敛** | 多位专家并行 → 编排者综合 | 问题能从同时存在的多元视角中获益 |

## 路由决策

对每个子任务回答：
1. 哪个角色拥有正确的方法论？
2. 该角色当前可用还是受阻？
3. 该角色需要前序角色提供什么？
4. 后续角色需要该角色提供什么？

## 条件角色

- `researcher`：仅在外部事实、技术选型或证据不足时参与。
- `technical-architect`：仅在契约、数据模型、部署拓扑或质量属性受到影响时参与。
- `backend-engineer` 与 `frontend-engineer`：按批准的系统拓扑参与；共享契约稳定后可以并行。
- `debugger`：仅在根因未知或故障反复出现时参与。
- `qa-engineer`：实现前定义验证策略，实现后执行测试和质量门。
- `reviewer`：在独立上下文中检查基线符合性、工程质量和已有验证证据。
