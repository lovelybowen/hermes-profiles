# Spec 模板

一份工程师、设计师和干系人都能使用的需求文档。目标不是规定每个像素和代码路径——而是对**我们在构建什么、不在构建什么、还没想清楚什么**达成对齐。

## 问题陈述

我们在解决什么问题、为谁解决？一段话。如果描述问题时离不开你的方案，说明思考得还不够。

**不要写：**「我们需要批量编辑功能，让用户一次编辑多项。」

**要写：**「管理 50+ 项目的高级用户每周花 4+ 小时逐个更新项目设置。每次设置变更需要 4 次点击和一次页面加载。这给单个用户可管理的项目数设了上限。」

## 成功指标

我们怎么知道这起效了？一个定量指标 + 一个定性信号。

- **主指标：** [如：每次项目设置更新耗时]
- **目标：** [如：从每周 4 小时降到 30 分钟]
- **定性信号：** [如：用户不再在支持工单里要批量编辑]
- **观察的反指标：** [如：不要增加误编辑——监控撤销/重做率]

## 范围

### 我们要构建的

3-6 个要点描述这个功能实际做什么。工程师可读。不含实现细节。

- 用户可以在列表视图选择多个项目
- 用户可以对所有选中项目一次性应用设置变更
- 用户可以在应用前预览变更
- 用户可以撤销最近一次批量操作
- 变更按项目逐条记录审计日志

### 我们不构建的

明确写出。这保护团队不被范围蔓延侵蚀。

- 不做定时/周期性批量操作（未来）
- 不做跨不同条目类型的批量操作（项目 + 任务混合）
- 不做基于模板的批量操作
- 不做批量操作的按角色权限（所有项目编辑者都可批量编辑）

## 开放问题

每份 spec 都应有开放问题。如果开放问题为零，要么你对问题理解完美，要么（更可能）你没想困难的部分。

- [ ] 选择多少条目之后性能开始退化？
- [ ] 批量操作应按条目生成独立审计记录，还是一条聚合记录？
- [ ] 是否存在用户能看到却无权批量编辑的权限场景？
- [ ] 这如何与现有的「项目锁」功能交互？

## 推迟的决定

明确决定现在不决定的事，附理由。

| 决定 | 推迟原因 | 何时重审 |
|----------|-------------|-----------------|
| 撤销窗口时长 | 需要 UX 研究 | 首批用户测试后 |
| 移动端布局 | 移动流量占高级用户 <5% | 移动流量超过 15% 时 |

## 设计约束

任何方案都必须满足的硬约束。来自团队，不是 PM 拍的。

- **工程：** 100 个条目的编辑操作须在 5 秒内完成
- **设计：** 须同时支持全宽和半宽视口配置
- **数据/基础设施：** 审计日志须维持现有不可变保证
- **无障碍：** 键盘导航须满足 WCAG 2.1 AA

## 边界情况

方案应处理的已知边界情况。已处理或已推迟。

| 边界情况 | 状态 |
|-----------|--------|
| 用户选中了无编辑权限的条目 | 预览中跳过并通知用户 |
| 批量操作部分失败 | 全部回滚并通知用户 |
| 待处理操作期间用户离开页面 | 取消操作并警告用户 |
| 选中期间条目被其他用户删除 | 刷新选中集，排除已删条目 |

## 技术说明

面向工程师的实现指引。PM 不指定架构，但可以浮出团队需要的上下文。

- 现有项目设置 API 支持单项 PATCH——需要批量 PATCH 端点
- 审计事件 schema 已含 `action:bulk_update`——无需 schema 迁移
- 撤销需要在审计事件上加新的 `bulk_operation_id` 关联字段

## 依赖

- 批量 PATCH 端点（API 团队，sprint +1）
- 预览弹窗的设计评审
- 确认消息的文案评审
- 键盘导航流程的无障碍审计

## 时间线与里程碑

| 里程碑 | 目标 | 退出标准 |
|-----------|--------|---------------|
| API 端点就绪 | Sprint+2 | 批量 PATCH 通过集成测试 |
| 前端原型 | Sprint+3 | 选择 + 预览流程在 staging 可用 |
| 用户测试 | Sprint+4 | 3/5 高级用户无引导完成任务 |
| 发布 | Sprint+5 | GA 且指标追踪已启用 |

## 风险

| 风险 | 可能性 | 影响 | 缓解 |
|------|-----------|--------|------------|
| 并发编辑冲突 | 中 | 高 | 项目设置悲观锁 |
| 1000+ 条目性能 | 低 | 中 | v1 选中上限 200 条 |
| 用户误应用错误设置 | 中 | 高 | 预览步骤 + 30 秒内撤销 |
