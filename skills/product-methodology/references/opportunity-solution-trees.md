# 机会解决方案树

Teresa Torres 的框架，用于把期望成果与要构建的东西连接起来——而不跳到方案。

## 结构

```
期望成果
└─ 机会 1（客户需要、痛点或渴望）
   ├─ 方案 A
   │  └─ 实验 1
   │  └─ 实验 2
   └─ 方案 B
      └─ 实验 1
└─ 机会 2
   ├─ 方案 C
   │  └─ 实验 1
   └─ 方案 D
```

**顶层：**期望成果——你希望为真的东西（「把试用转付费从 12% 提高到 18%」）。

**中层：**机会——如果被解决就能推动成果的客户需要、痛点或渴望。不是方案。「客户看不懂定价页」是机会。「重新设计定价页」是方案。

**底层：**方案——可以构建的东西。每个方案是一个假设。每个方案下面是验证它的实验。

## 核心实践

### 1. 从成果出发

写下你要推动的可度量成果。要具体。「改进新手上手」太模糊。「把完成新手上手的用户比例从 40% 提高到 65%」是具体的。

### 2. 发现机会

与客户交谈。分析使用数据。找用户卡住的地方、发展变通的地方、表达受挫的地方。每个独立的需要是一个机会节点。

**好的机会陈述：**
- 「新用户在注册前不理解能得到什么价值」
- 「用户无法方便地与同事分享工作成果」
- 「高级用户需要自动化重复任务」

**坏的机会陈述（其实是方案）：**
- 「我们需要落地页放个视频」→ 方案，不是机会
- 「用户需要批量编辑」→ 方案，不是机会（机会是「用户一次管理一项，数量太多」）

### 3. 为每个机会生成方案

对每个机会，头脑风暴 3-5 个可能方案。包含非技术方案（流程改变、内容、合作）。最好的方案可能不是代码。

### 4. 先测最险的假设

对每个方案，找出既最关键又最不确定的假设。设计测试该假设的最小实验。

| 最险假设 | 最小测试 |
|--------------------|---------------|
| 用户想要这个 | 带「通知我」按钮的落地页 |
| 技术上可行 | 快速原型 |
| 用户能理解它 | 5 人可用性测试 |
| 比现行变通更好 | 并排对比测试 |

### 5. 随学习更新树

实验产出证据。用学到的东西更新每个节点。剪掉经不起现实检验的分支。添加从学习中涌现的新机会。

## 什么时候用

以下情况机会解决方案树是正确工具：

- 问题空间混乱，不确定要构建什么
- 干系人在没验证问题的情况下直接跳到方案
- 你已建了若干功能但都没推动成果
- 你需要一张共享的领地地图来对齐团队

## 反模式：过早方案化

最常见的失败：有人说出一个机会，整个房间立刻跳到「我们来建 X 吧」。树结构让这变得可见——如果你的树只有一个机会挂着六个方案，说明你跳过了发现。回去先找更多机会，再评估方案。

## 与其他框架的关系

| 框架 | 角色 |
|-----------|------|
| RICE | 排序下一步追求哪些机会/方案 |
| MoSCoW | 为某次发布圈定树的一个分支的范围 |
| 客户访谈 | 向树输入机会 |
| Spec 模板 | 为选定的方案撰写实现文档 |
