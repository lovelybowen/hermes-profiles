# 任务分解

## 分解规则

复杂问题需要从已确认需求基线分解为子问题，每个子问题交给拥有相应方法论的专家。基线必须能定位稳定标识、版本或哈希，以及角色、场景、流程、业务规则和验收标准；缺失或冲突时停止分解并交回 `Intent Owner`。

## 分解模式

| 问题类型 | 分解方式 | 专家 |
|--------------|---------------|-------------|
| “我们应该做 X 吗？” | 研究选项 → 分析约束 → 准备人类决策包 | researcher、technical-architect、人类责任人 |
| “按照基线构建 Y” | 校验基线 → 条件性架构分析 → QA 设计验证 → 实现切片 → QA 执行 → 独立评审 | orchestrator、按需专家、qa-engineer、reviewer |
| “调试 Z” | 复现 → 隔离 → 根因 → 修复 | debugger（全部阶段） |
| “评审 W” | 检查证据 → 识别风险 → 验证发现 | reviewer、qa-engineer |

## 分解检查清单

- [ ] 每个子任务范围清晰，专家无需额外上下文即可理解
- [ ] 每个子任务引用同一需求基线 revision 或 content hash
- [ ] 子任务顺序正确（先研究后分析，先起草后编辑）
- [ ] 子任务互不重叠，每位专家都有独立重点
- [ ] 条件角色只在触发条件成立时参与，跳过时记录原因
- [ ] 综合步骤明确所有子任务之间的关系
- [ ] 分解结果已形成审批计划（steps + skipped_experts），非豁免任务已按 `references/decomposition-approval.md` 过 DA 门（豁免：G0 与 L0 快速通道，豁免须记录）
