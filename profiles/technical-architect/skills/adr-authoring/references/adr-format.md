# ADR 格式与编写指南

本指南完整收录社区 ADR 仓库（https://github.com/architecture-decision-record/architecture-decision-record）中的架构决策记录格式，并按决策类型提供选择指引和实践示例。

## 模板选择指南

| 决策类型 | 推荐模板 | 原因 |
|---|---|---|
| 常规技术选择（库、框架） | **Nygard** | 轻量：状态、上下文、决策、后果 |
| 明确比较的多选项取舍 | **MADR** | 决策驱动因素 + 带优缺点的候选选项 |
| 高风险/监管/合规 | **Tyree & Akerman** | 12 个部分，覆盖问题、假设、约束、立场、论证、影响，以及相关决策/需求/产物/原则 |
| 供应商/采购/自建与采购 | **Business Case** | 评估准则、成本分析、SWOT、意见/建议 |
| QA 契约/SLA/非功能需求 | **Planguage** | 标签、要点、优先级、利益相关方、风险、定义术语 |
| 快速内部共识，无正式评审 | **Alexandrian** | 上下文特定、结构最小化 |
| 高管层/高管评审 | **ITD（Important Technical Decisions）** | 决策优先，针对高管快速浏览优化 |

## 模板目录

### 1. Michael Nygard（简单且常用）

**来源：**http://thinkrelevance.com/blog/2011/11/15/documenting-architecture-decisions

**使用时机：**理由直接且选项较少的日常决策。除非需要更多结构，否则将其作为默认选择。

```
# 标题（现在时祈使动词短语）

## 状态

proposed | accepted | rejected | deprecated | superseded by ADR-NNN

## 上下文

我们观察到了什么问题，促使做出这项决策或变更？

## 决策

我们建议和/或正在实施什么变更？

## 后果

这项变更会使哪些事情变得更容易或更困难？
```

**章节指引：**
- **标题：**简短的祈使短语，例如“使用 PostgreSQL 存储事务”或“在服务之间采用事件驱动消息传递”
- **状态：**单一值。使用生命周期阶段可获得更高精度。
- **上下文：**正在发挥作用的因素——业务需求、技术约束、团队能力、时间线压力。说明为何要在*现在*做出此决策。
- **决策：**结果。具体且无歧义。写“我们将使用 X”，而不是“我们考虑过使用 X”。
- **后果：**同时记录正面和负面后果。接受了哪些取舍？这会产生哪些后续决策？

**常见陷阱：**
- 对需要明确比较选项的多利益相关方决策而言过于简略
- 没有自然位置记录决策驱动因素
- 容易跳过“后果”，尽管它是最重要的章节

### 2. MADR——Markdown Any Decision Records（结构化）

**来源：**https://adr.github.io/madr/

**使用时机：**大多数涉及多个选项并明确比较取舍的决策。对多数工程团队而言，这是最佳默认选择。

```
# [已解决问题和解决方案的短标题]

* Status: proposed | rejected | accepted | deprecated | superseded by ADR-NNN
* 决策者：[列出所有参与决策的人]
* Date: YYYY-MM-DD

技术故事：[说明 | 工单/issue URL]

## 上下文与问题陈述

[说明上下文和问题陈述。可以考虑以问题形式
 表述该问题。]

## 决策驱动因素

* [驱动因素 1，例如作用力、面临的关注点]
* [驱动因素 2]
* ...

## 候选选项

* [选项 1]
* [选项 2]
* [选项 3]

## 决策结果

选定选项：“[选项 1]”，因为[理由]。

### 正面后果

* [例如，提高质量属性满足度]
* ...

### 负面后果

* [例如，牺牲质量属性]
* ...

## 各选项的优缺点

### [选项 1]

* 优点，因为[论据 a]
* 优点，因为[论据 b]
* 缺点，因为[论据 c]

### [选项 2]

* 优点，因为[论据 a]
* 缺点，因为[论据 b]

## 链接

* 由 [ADR-0005](0005-example.md) 细化
* 取代 [ADR-0002](0002-example.md)
```

**章节指引：**
- **决策驱动因素：**任何解决方案都必须满足的不可协商约束。这些就是选择准则。如果决策不需要明确准则，考虑改用 Nygard。
- **候选选项：**应足够完备，使评审者不会询问“是否考虑过 X？”，但又不能详尽到形成噪声。通常为 3-5 个选项。
- **优缺点：**每个选项都有自己的小节，以要点列出优缺点。表述要具体——写“优点，因为在峰值负载下降低 40% 延迟”，而不是“优点，因为更快”。
- **链接：**与相关 ADR 建立双向链接。使用有语义的链接类型：取代、细化、冲突、扩展。

**常见陷阱：**
- “候选选项”章节可能膨胀。最多保留 5 个选项，将相似替代方案归组。
- 决策驱动因素经常只列出、不排序。应设置优先级（必须具备与最好具备）。

### 3. Jeff Tyree 与 Art Akerman（重量级/企业级）

**来源：**https://www.utdallas.edu/~chung/SA/zz-Impreso-architecture_decisions-tyree-05.pdf

**使用时机：**具有监管、合规或跨团队影响的高风险决策，以及未来多年都会被审计或引用的决策。

| 章节 | 目的 |
|---|---|
| **问题** | 正在处理的架构设计问题，并明确说明为何是*现在* |
| **决策** | 架构方向——选定的立场 |
| **状态** | 待定、已决定、已批准 |
| **分组** | 本体分组：集成、展示、数据、事件、日历、位置 |
| **假设** | 底层环境假设（成本、进度、技术、已接受标准） |
| **约束** | 所选替代方案施加的额外约束 |
| **立场** | 考虑过的可行选项。包含模型、图。这可避免评审时出现“是否考虑过 X？” |
| **论证** | 选择该立场的原因：实施成本、TCO、上市时间、资源可用性。与决策本身同等重要 |
| **影响** | 后续效应：新增必需决策、新增/修改需求、额外约束、范围/进度变化、培训需求 |
| **相关决策** | 可追溯矩阵、决策树或元模型。链接到相关 AD 决策 |
| **相关需求** | 直接映射到业务目标。如果决策对任何需求都没有贡献，就不要做出该决策 |
| **相关产物** | 受此决策影响的架构、设计或范围文档 |
| **相关原则** | 此决策遵循的企业原则。确保跨系统一致 |
| **说明** | 社会化过程中的持续记录 |

**不应使用：**常规选择、单个开发人员的决策、临时变通方案。

### 4. Business Case（采购/供应商）

**使用时机：**自建与采购、供应商选择、技术采购——成本和组织影响是主要驱动因素的决策。

**顶层结构：**
- 标题
- 状态
- 评估准则
- 待考虑候选项
- 对每个候选项的研究和分析
  - 满足/不满足准则
  - 成本分析（许可、培训、运营、计量）
  - SWOT 分析（优势、劣势、机会、威胁）
  - 内部和外部意见/反馈
- 建议

**成本分析维度：**
- **许可：**合同协议、法律承诺、供应商锁定风险
- **培训：**技能提升、变更管理、上手时间
- **运营：**支持、维护、事件响应
- **计量：**带宽、CPU、API 调用、数据传出

**常见陷阱：**
- 外部意见可能偏向供应商推荐的方案。进行交叉核对。
- 成本估算很快过时——为所有定价引用添加日期戳。

### 5. Planguage（聚焦 QA/NFR）

**来源：**Tom Gilb，https://www.iaria.org/conferences2012/filesICCGI12/Tutorial%20Specifying%20Effective%20Non-func.pdf

**使用时机：**由质量属性、SLA 或非功能需求驱动，且精确性和可衡量性很重要的决策。

| 关键词 | 目的 |
|---|---|
| **Tag** | 唯一、持久的标识符 |
| **Gist** | 需求或领域的简要摘要 |
| **Requirement** | 需求文本 |
| **Rationale** | 证明需求合理的推理 |
| **Priority** | 优先级和资源诉求声明 |
| **Stakeholders** | 受到实质影响的相关方 |
| **Status** | 草稿、已评审、已承诺 |
| **Owner** | 负责实施的人员 |
| **Author** | 编写人员 |
| **Revision** | 版本号 |
| **Date** | 最近修订日期 |
| **Assumptions** | 如果不成立，可能导致问题的事项 |
| **Risks** | 可能导致故障或延迟的事项 |
| **Defined** | 术语表中的术语 |

### 6. Alexandrian Pattern（上下文优先）

**使用时机：**上下文是主要驱动因素、且解决方案空间受到严格约束的决策。

```
## [标题]

## 上下文

[正在发挥作用的因素——此模式何时适用？]

## 问题

[此决策解决的具体问题]

## 解决方案

[决策，以解决这些作用力的方式陈述]

## 后果

[应用此解决方案后会发生什么]
```

### 7. Important Technical Decisions——ITD（高管）

**来源：**Ignacio Larrañaga

**使用时机：**需要高管签字确认的决策。精简且决策优先——针对快速浏览优化，而非详细审议。

```
# [决策标题]

## 决策

[用一行说明做出了什么决定]

## 原因

[简要理由——为何是这项决策，为何是现在]

## 影响

[因此发生什么变化——一段]
```

### 8. arc42 ADR 模板（完整文档结构）

**来源：**https://arc42.org/overview——许可证：CC-BY-SA 4.0

**使用时机：**需要在完整 arc42 架构文档框架中记录的决策。这是 arc42 团队提供的 ADR 专用模板，与 arc42 完整文档模板不同（后者由 `arc42-context` 技能用于系统上下文/约束文档）。

**章节：**

| arc42 章节 | 目的 |
|---|---|
| **1. 引言与目标** | 需求、驱动力、质量目标、利益相关方 |
| **2. 约束** | 限制设计/实施自由度的任何事项 |
| **3. 上下文与范围** | 系统边界、外部接口、业务/技术上下文 |
| **4. 解决方案策略** | 塑造架构的根本决策 |
| **5. 构建块视图** | 静态分解——模块、组件、层 |
| **6. 运行时视图** | 通过场景描述行为——用例、错误、操作 |
| **7. 部署视图** | 基础设施、环境、构建块映射 |
| **8. 横切概念** | 跨越多个构建块的模式、规则、法规 |
| **9. 架构决策** | 包含理由的重要决策（这才是 ADR 正文） |
| **10. 质量需求** | 质量场景、质量树 |
| **11. 风险与技术债** | 已知风险、债务；按优先级排序 |

**与 arc42-context 技能的关系：**我们的 arc42-context 技能使用完整 arc42 模板，在项目层记录系统约束。此 ADR 模板是一个*轻量版本*，聚焦该框架中的单项决策。在现有 arc42 文档内记录决策时使用此模板。

### 9. EdgeX 模板（平台/IoT）

**来源：**https://docs.edgexfoundry.org/2.3/design/adr/template/

**使用时机：**涉及平台组件、服务边界或 API 变更的决策——尤其是影响多个服务的 IoT/边缘场景。

```
# [标题]

## 提交者

- 姓名（组织）

## 变更日志

- [状态](PR URL) YYYY-MM-DD
  状态：待定、已批准、已修订、已弃用。

## 引用的用例

- [用例名称](URL)

## 上下文

- 此设计为何具有架构重要性
- 高层设计方法

## 拟议设计

不涉及实现的细节：

- 受影响（变更）的服务/模块
- 待添加的新服务/模块
- 对模型和 DTO 的影响（新增/删除）
- 对 API 的影响（新增/删除）
- 对配置的影响
- 对 DevOps 的影响

## 考虑事项

讨论中提出的替代方案、关注点和问题，以及解决状态。

## 决策

限制条件、未来考虑事项、剩余或延后问题。
拟议设计未满足的需求。

## 其他相关 ADR

- [ADR 标题](URL)——相关性

## 参考资料
```

**显著特征：**包含状态/日期/PR URL 的变更日志；引用的用例；异常详细的拟议设计（模型/DTO/API/配置/DevOps）。适用于 ADR 同时作为决策记录**和**初步设计文档的情况。

### 10. Gareth Morgan 模板（摘要驱动）

**来源：**Gareth Morgan

**使用时机：**需要先提供高管摘要、再进行结构化选项分析的决策。摘要 → 驱动因素 → 选项 → 分析 → 建议的结构与现代产品决策相呼应。

```
# [标题]

**状态：**拟议 | 评审中 | 已接受 | 已拒绝 | 已取代 | 已弃用
**更新时间：**YYYY-MM-DD

## 摘要

高管摘要/电梯陈述。用 2-4 句话说明核心问题，
并提示决策。可将其视为技术论文摘要。

## 驱动因素

为何现在做出这项决策：

- {我们正在开发一项需要……的新功能}
- {我们需要改进性能、可访问性……}
- {当前方法施加了限制……}

## 选项

包含事实和链接的选项列表：

### {选项 1}
说明

### {选项 n}
...

## 选项分析

### {选项 1 评估}
- 优点：{具体优势}
- 缺点：{具体劣势、风险或成本}
- 其他：{相关要点}

### {选项 n 评估}
...

## 建议

清晰陈述最终决策，以及它为何最能满足驱动因素。

### 后果

- 优点：{正面结果}
- 缺点：{已接受的不利影响或风险}
- 其他：{客观后果}

### 确认

- 如何验证实现（评审、测试、演示）
- 如何维持合规（自动检查、审计）
- 显示预期结果的指标/指示器
- 负责的所有者

## 更多信息

补充信息、链接、重新评估时限。
```

**显著特征：**摘要优先（先做电梯陈述，再提供细节）；明确的驱动因素章节（为何是*现在*）；将后果分为优点/缺点/其他；**确认章节**——包含合规监控、指标和所有权的验证计划。这在 ADR 模板中很少见，但对高风险决策至关重要。

### 11. GIG Cymru NHS Wales 模板（聚焦治理）

**来源：**NHS Wales / GIG Cymru

**使用时机：**需要合规监控、治理和可视化选项分析的受监管环境（医疗、金融、基础设施）。

```
# [标题]

**Status:** DRAFT | ACTIVE | DEPRECATED by [000] | SUPERSEDES [000]

## 上下文

此 ADR 解决的问题及其存在原因。

## 已决定的方法

具有架构重要性的决策，以及它如何解决问题。

## 后果

对架构特征和功能需求的影响。

## 治理

如何监控结果？如何确保合规？

## 选项分析

使用交通灯对比表进行取舍分析。

### 图例

绿色 = 高度匹配  琥珀色 = 中等  红色 = 匹配度低
+ = 正面评价  - = 负面评价

### 高层概览

| 摘要 | 选项 1 | 选项 2 | 选项 3 |
|---|---|---|---|
| 实施难易度 | + 快速（绿色） | - 棘手（琥珀色） | - 复杂（红色） |
| 时间尺度 | + 快（绿色） | - 慢（琥珀色） | - 非常慢（红色） |
| 战略价值 | - 战术性（红色） | + 有改善（琥珀色） | + 理想（绿色） |

### 功能需求

| 场景 | 选项 1 | 选项 2 | 选项 3 |
|---|---|---|---|
| 场景 1 | | | |

### 非功能需求

| 特征 | 选项 1 | 选项 2 | 选项 3 |
|---|---|---|---|
| 可扩展性 | | | |
| 性能 | | | |
| 可用性 | | | |
```

**显著特征：****治理章节**——在模板中独树一帜，明确询问合规监控。**交通灯对比表**——在摘要、功能和 NFR 维度提供颜色编码的可视化评估。专为必须执行而非仅记录决策的受审计环境设计。

### 模板选择决策树

```
决策是否快速且只有一个理由？
  → 是 → Nygard
  → 否 → 是否比较多个选项？
    → 是 → 是否有监管/治理要求？
      → 是 → 是否需要合规监控？
        → 是 → NHS Wales（治理 + 交通灯表）
        → 否 → 成本是否为主要驱动因素？
          → 是 → Business Case（成本/SWOT）
          → 否 → 是否变更平台/服务边界？
            → 是 → EdgeX（变更日志 + 拟议设计）
            → 否 → MADR（结构化选项比较）
      → 否 → MADR（多选项的默认选择）
    → 否 → 是否由 QA/NFR 驱动？→ Planguage
    → 否 → 是否供高管层使用？→ ITD
    → 否 → 是否上下文优先？→ Alexandrian
```

## 实践示例：MADR 格式

```
# 使用 PostgreSQL 存储服务事务

* Status: accepted
* 决策者：Magnus Hedemark、Sarah Chen、DevOps 团队
* Date: 2026-06-05

技术故事：服务需要持久、符合 ACID 的存储，以保存
跨地理区域的客户事务记录。

## 上下文与问题陈述

服务需要以强一致性保证存储客户事务数据。
当前原型使用内存存储，这对生产环境不可接受。
我们需要一个支持 ACID 事务和跨区域复制，
且拥有可靠运营记录的数据库。

## 决策驱动因素

* 必须支持 ACID 事务（不可协商——监管要求）
* 必须支持跨 2 个区域的主备复制
* 团队已有 PostgreSQL 专业能力（3 名高级 DBA）
* 必须符合现有每月 $500 的基础设施预算

## 候选选项

* PostgreSQL——关系型、ACID、成熟复制（pglogical/Patroni）
* MySQL——关系型、ACID、Group Replication
* CockroachDB——分布式 SQL、原生多区域
* DynamoDB + 事务——具有有限 ACID 能力的托管 NoSQL

## 决策结果

选定选项：“PostgreSQL”，因为它满足所有决策驱动因素，
消除了团队学习曲线，并且在我们的
规模下运营成本最低。

### 正面后果

* 在现有团队专业能力范围内保证 ACID 合规
* 通过 Patroni 实现主备复制（本周部署）
* 无许可成本；符合基础设施预算

### 负面后果

* 超过 5TB 后可能需要手动分片（第 1 年不太可能）
* 主备模式存在单写入方限制

## 各选项的优缺点

### PostgreSQL

* 优点，因为提供具有可串行化隔离的完整 ACID
* 优点，因为团队已有专业能力，无需上手时间
* 优点，因为复制工具成熟（Patroni、repmgr）
* 缺点，因为单写入方拓扑限制写入吞吐量

### MySQL

* 优点，因为 InnoDB 支持 ACID
* 优点，因为 Group Replication 支持多写入方
* 缺点，因为团队专业能力较少（MySQL 只有 1 名 DBA，Postgres 有 3 名）
* 缺点，因为 Group Replication 在异步模式下存在已知稳定性问题

### CockroachDB

* 优点，因为原生支持具有强一致性的多区域部署
* 缺点，因为同等硬件的基础设施成本为 2 倍
* 缺点，因为运营复杂性需要专职 SRE 支持

### DynamoDB + Transactions

* 优点，因为运营开销为零
* 缺点，因为事务 API 存在 25 个条目/4MB 的限制
* 缺点，因为被 AWS 供应商锁定
* 缺点，因为规模化后每个副本每小时 $0.50 会超出预算
```

## 架构决策日志（ADL）约定

### 文件命名

```
NNN-short-present-tense-phrase.md
```

规则：
- **编号：**补零序列（001、002、……010）。避免空缺；发生冲突时重新编号。
- **短语：**现在时祈使动词短语——类似一条优秀的提交消息。
  - 良好：`012-use-postgresql-for-transaction-storage.md`
  - 糟糕：`012-postgresql.md`（没有动词）、`012-decided-to-use-postgresql.md`（过去时）
- **大小写：**小写并使用连字符（kebab-case）。
- **扩展名：**使用 `.md`，便于渲染。

### 目录命名

考虑将目录命名为 `decisions/` 而不是 `adr/`——一些团队更容易接受直白语言。该模板对内容保持中立；可以用相同格式记录供应商决策、规划决策和排期决策。

### 编号方案

- 在整个项目中连续编号（而不是按类别编号）
- 绝不复用编号——如果 ADR 被拒绝，该编号保持停用
