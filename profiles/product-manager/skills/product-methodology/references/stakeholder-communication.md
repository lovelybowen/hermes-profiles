# 干系人沟通

不同受众需要不同容器里的不同信息。PM 的技能不只是知道说什么——而是知道对**谁**说什么。

## 对高管

### 格式

```
建议：[一句话]
原因：[2-3 句]
需要的决策：[具体请求，附截止时间]
坏消息：[如有，尽早浮出]
```

### 规则

**以建议开头。**高管不需要走过你的分析才到结论。先给答案。他们想看方法论会自己问。

**坏消息尽早浮出。**趁还没变成危机。一个从客户那里（而不是从你这里）先听到延期的高管已经失去了信任。格式：

> 我们将错过 [功能] 的 [日期] 发布。我们于 [何时] 发现。根因是 [具体——不指名批评]。我们的应对是：[计划]。[日期] 前会有进一步消息。

**不在状态报告里藏决策。**需要决策就单独提请求。不要在周报里埋一句「顺便说下，我们是不是应该……」。

**包含反方观点。**如果你建议方案 A，简短说明为什么有人可能选 B、而你为何仍选 A。它预先回应了疑问，也表明你考虑过替代项。

### 反模式

- **PPT 优先思维。**沟通不需要幻灯片。结构良好的段落读得更快、更难误读。
- **二十页巡礼。**你探索过方案 A、B、C、D。告诉他们你选了 A 以及为什么。不要带他们逐个走一遍。
- **乐观偏误。**「我们也许能把时间追回来」不是计划。给他们当前预测，不是希望。

## 对工程师

### 格式

一份 spec 文档（见 `references/spec-template.md`）。但日常的活沟通遵循不同规则。

### 规则

**具体且诚实。**标记你知道什么、不知道什么、哪些决定被推迟。工程师被假装有答案的 PM 坑过。

**解释优先级变化背后的「为什么」。**不只是「领导层决定了」——而是实际的考量与权衡。理解业务上下文的工程师做出更好的技术决定。

**不替他们做承诺。**「工程说这要两周」没问题。「我跟干系人说了两周」是你没经他们输入就做的承诺。

**尽早带入约束。**技术、业务、时间线——在工程开始设计之前告知，而不是建错东西之后。

**标记开放问题。**每份 spec 都该有一节叫「开放问题」。工程师反正会发现——预先列出能建立信任。

### 反模式

- **接单员模式。**「这是 spec，去建吧。」最好的工程产出来自让他们参与问题，而不只是方案。
- **范围突袭。**估算完成后追加需求。范围变了就重新估算。
- **不响应。**工程师问了个 spec 问题。24 小时不回，你就制造了一个阻塞。哪怕回「我去确认」也算回应。

## 对设计师

### 格式

结果描述，不是像素 spec。

### 规则

**对结果具体，对实现灵活。**用可度量术语描述成功，不指定 UI。「用户需要知道哪些团队成员现在在线」是好的简报。「每个头像旁要有个绿点」是坏的。

**尽早带入约束。**技术、业务、时间线。让设计师在探索前就知道约束，他们的工作才不会因为不可控的原因被否决。

**以伙伴而非批准人身份评审。**反馈框定在用户行为上，不是个人偏好。「这个交互没处理用户未完成上手的情况」有用。「我不喜欢这个蓝」没用。

**保护探索时间。**像保护工程心流一样。一个每一小时探索都要辩护的设计师会停止探索。

### 反模式

- **「让它更跳」。**描述不出什么不对，大概率也描述不出什么是对的。
- **跳过问题空间。**需求锁定后才把设计师拉进来，浪费了他们最好的技能——在含混中解决问题。
- **反馈轮轰炸。**三轮设计反馈通常说明你预先没给足够清晰的约束。

## 对客户

### 格式

倾听模式。问上一次。观察而不引导。注意犹豫、受挫、变通。

### 规则

**问行为，不问观点。**「讲讲你上一次尝试做 X」产出事实。「如果我们建了 Y 你会用吗」产出客气。

**不捍卫产品。**客户挣扎，那就是数据。如果你跳进去演示「正确用法」，信号就丢了。

**承诺是债。**「我们会修的」是承诺。「这有意思——多说说」是学习。别混淆两者。

**闭环。**客户为访谈给了时间，就告诉他们产出了什么——哪怕答案是「我们学到那不是该解决的问题」。这为下一次对话建立信任。

### 反模式

- **销售模式。**你的产品有缺陷。客户指出来不是攻击——是研究数据。
- **钓方案。**「你愿意为 X 付钱吗？」被真要求付款前没人知道。问他们现在的成本。

## 对所有人

| 原则 | 为什么 |
|-----------|-----|
| 坏消息尽早浮出 | 坏消息不会随时间变好 |
| 不知道就说「不知道」 | 假装浪费所有人的时间 |
| 解释推理，不只是决定 | 理解建立信任 |
| 写下来 | 口头协议有半衰期 |
| 带时间戳跟进 | 没有跟进的「我去查」毫无意义 |
