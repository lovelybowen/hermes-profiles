# 安全评审

在漏洞进入生产环境之前，于代码中系统化发现漏洞的方法。

## 档位与核验深度

安全相关任务（含 T6）的证据档位为 **`Full`**：交接的 `evidence_level` 必须为 `Full` 且携带 `seb_integrity: passed`，核验深度按 `references/evidence-level-verification.md` 的 `Full` 档**全量执行**（build / browser / diff / SHA 逐项复算），不得以抽样替代或降档放行。档位阈值与 SEB 判定的唯一权威出处是 `skills/artifact-pyramids/references/evidence-levels-and-seb.md`；交接字段名以 `skills/orchestration-methodology/references/delivery-governance.md` §6 为准。

## 安全评审思维

不同于代码评审，安全评审假定代码存在问题，并寻找证明方式。要问的不是“它是否正确工作？”，而是“攻击者会如何利用它？”

## 评审中的威胁建模

查看单独代码路径前，先勾勒威胁模型：

| 元素 | 要问的问题 |
|---------|-------------|
| **资产** | 这段代码保护什么？（数据、凭据、访问权限、算力） |
| **攻击者** | 谁会试图攻破它？（外部攻击者、恶意内部人员、依赖） |
| **攻击面** | 攻击者可以触及哪些入口？（API 端点、文件输入、用户提供数据） |
| **信任边界** | 数据在哪里从不可信上下文跨入可信上下文？（输入解析、反序列化、exec 调用） |
| **权限级别** | 进程可以做哪些本不该做的事情？（root、数据库访问、网络） |

## 要检查的漏洞类别

### 注入（严重）
- **Shell 注入：**用户输入被拼接进 Shell 命令。标记：`os.system()`、带 `shell=True` 的 `subprocess.Popen()`、命令中的 f 字符串。修复：使用 `shlex.quote()` 或以参数列表调用 `subprocess.run()`。
- **SQL 注入：**SQL 字符串中包含用户输入。标记：SQL 中的 f 字符串或 `+` 拼接。修复：参数化查询。
- **命令注入：**用户输入位于 CLI 标志值中。标记：未经验证的不可信数据作为 `--flag value` 传入。

### 反序列化（严重）
- **Pickle：**反序列化时可执行任意代码。标记：来自不可信来源的 `pickle.loads()`。修复：使用 JSON 或结构化格式。
- **YAML：**对不可信输入使用 `yaml.load()` 可执行代码。修复：`yaml.safe_load()`。
- **带 eval 的 JSON：**`json.loads()` 后跟 `eval()`，视为严重问题。

### 认证与授权（严重）
- **硬编码凭据：**源代码中的 API 密钥、令牌或密码。标记：Python 文件中的 `API_KEY = "sk-..."`。修复：使用环境变量或密钥管理器。
- **缺少认证检查：**本应要求认证的端点或函数没有检查。
- **权限提升：**用户可以访问本不应访问的资源。检查 URL 中的对象 ID 和角色检查。

### 路径遍历（高）
- **未验证的文件路径：**用户输入用于构造文件路径。标记：`open(user_input)`、带用户输入的 `os.path.join()`。修复：使用 `os.path.realpath()` 并检查前缀。
- **符号链接攻击：**代码跟随符号链接访问非预期文件。修复：访问控制检查前使用 `os.path.realpath()`。

### 信息泄露（高）
- **生产环境堆栈跟踪：**未捕获异常泄露内部状态。
- **过于详细的错误消息：**“用户不存在”与“密码无效”相比，前者会泄露有效用户名。
- **记录秘密信息：**日志输出中包含 API 密钥、令牌或密码。标记任何 `logger.info(f"secret={token}")`。

### 供应链（中高）
- **固定依赖版本：**检查 `requirements.txt`、`pyproject.toml`、`package.json` 是否存在未固定版本。
- **已弃用软件包：**检查已知有漏洞的依赖，如 `pip audit`、`npm audit`、`grype`。
- **生产环境中的开发依赖：**标记生产 Docker 镜像中安装的仅开发使用的软件包。

### 密码学（中）
- **自研密码算法：**自定义加密、散列或随机数生成。标记任何从头实现 AES、SHA 或 RNG 的代码。
- **弱算法：**在安全场景使用 MD5、SHA-1。应标记并建议 SHA-256 以上或 bcrypt/argon2。
- **硬编码 IV 或密钥：**静态初始化向量或加密密钥。

## 安全评审协议

### 阶段 1：绘制攻击面
1. 列出所有入口点，例如 API 路由、文件加载、网络连接和用户输入。
2. 列出所有信任边界，即处理未经验证数据的位置。
3. 列出所有权限上下文，即每个组件在何种访问级别下运行。

### 阶段 2：扫描漏洞类别
1. 针对上述类别运行自动检查，例如 grep 危险模式。
2. 针对每个匹配项阅读周边实际代码，上下文才能区分信号和噪声。
3. 将发现分类为：已确认（可利用）、可疑（需要深入调查）、无害（在上下文中不可利用）。

### 阶段 3：评估可利用性
针对每个已确认发现：
- **是否可从不可信输入触及？**如果可以，即可利用；否则属于纵深防御。
- **影响是什么？**数据暴露、RCE、权限提升还是拒绝服务？
- **是否已有缓解措施？**例如限流、沙箱或 WAF 规则。

### 阶段 4：报告
针对每个发现，提供：
1. 文件和行号。
2. 漏洞类别。
3. 危险代码模式（摘录）。
4. 为何可利用，或为何不可利用。
5. 修复建议。

## 安全发现的严重程度

| 严重程度 | 影响 | 行动 |
|----------|--------|--------|
| 🔴 严重 | RCE、权限提升、凭据暴露 | 阻断，合并前必须修复 |
| 🟠 高 | 数据暴露、路径遍历、认证绕过 | 阻断，合并前必须修复 |
| 🟡 中 | 加固、缺少最佳实践 | 应修复，可讨论 |
| 🔵 低 | 纵深防御、信息性问题 | 记录供后续改进 |
